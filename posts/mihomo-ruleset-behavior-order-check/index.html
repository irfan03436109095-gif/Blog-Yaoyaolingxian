Mihomo 规则集下载成功却没命中？先核对内容格式和规则顺序

加油2026-11-25— 次阅读
故障排查

机场客户端里规则集的更新时间变了，访问网站时却还是走原来的策略组。下载或更新成功、核心读取规则集、这次连接命中规则是三条不同证据。 下面只针对使用 Mihomo 核心的规则模式；别拿另一个客户端的菜单或配置语法硬套。

先看文件写的是什么条目

在客户端当前加载的配置里找到 rule-providers。除去 provider 的名称和值，再核对 format 与 behavior：前者描述怎么读文件，例如 YAML 或文本；后者决定里面是什么规则。下面只展示条目的长相，不是整份可直接覆盖的配置。

  • domain 写域名或符合 Mihomo 规则的通配模式，例如 example.com，不是一行带规则类型的 DOMAIN,example.com。
  • ipcidr 写 IP 网段，例如文档用途的 192.0.2.0/24，不能把域名直接放进去。
  • classical 支持多种带类型的路由规则，例如 DOMAIN,example.com；不要在其中再套 RULE-SET 或 SUB-RULE。

例如拿到文本文件却声明成 YAML，或把带 DOMAIN, 的条目交给 domain，就应先核对处理方式和核心日志。浏览器能打开文件 URL 或客户端显示“已下载”，不代表运行时读入了有意义的条目。

示意图：规则文件能读取只是第一步，请求还要走到引用它的那条规则并实际命中。

看请求有没有走到这一行

在生效的 rules 中找到 RULE-SET,规则集名称,策略名，核对引用名称和 provider 名称完全一致。下载或更新规则集经过的代理字段与这里指定的分流策略不是一个东西。Mihomo 按规则从上向下匹配；在日常 HTTPS 的对照里，前面若有已经命中的全域规则或兜底匹配，后面的规则即使写对也到不了。别为了试一条规则把所有规则段重排；在备份的测试配置中仅调整一处。

一条命中加一条负对照

用公开的示例域名构造测试：同一客户端、同一模式下，对含在测试规则集里的 example.com 发起新连接，对未包含的 example.org 再发起一条。观察客户端连接详情或核心日志里实际命中的规则、目标和出站，不单看页面是否打开或两个策略组名字是否相同。验收通过是第一条明确命中这条 RULE-SET、第二条不命中它；如果两条都找不到记录，先确认应用的流量确实进入当前核心。记录修改前后差别，不复制带订阅凭据的原配置。
