Mihomo 健康检查标红，网页却能打开？核对测试地址和预期状态码

加油2026-11-27— 次阅读
故障排查

浏览器用某个机场节点能打开网页，Mihomo 的定时健康检查却把它标红。先不要把它记作线路彻底中断：这个检查用指定地址做一项小测试，配置了 expected-status 时，还会要求回应状态符合预期。测试地址失效、状态不匹配或者使用了另一套检查配置，都可能让图标与真实任务不一致。

找到实际生效的那组字段

先确认当前加载的是哪份配置，以及节点是写在策略组 proxies 列表里，还是由 use 引入代理提供器。按官方文档，组的 url 检查 proxies，并不直接检查 use 中引入的提供器节点。后一种应在对应的 proxy-providers 项下找 health-check，核对是否启用、地址、间隔及预期状态。只改组的 URL 后观察提供器的灯，可能改错了对象。

示意图。实际任务能访问，与指定测试地址返回了预期状态，是两项不同的检查。

先核对一对值，别把标红改成全绿

比如自有测试端点设计成返回 204，但迁移路径后改成返回 200。只要配置仍要求 204，200 与要求就不匹配；这不是一次实际测速结论。expected-status 默认 * 表示不限制响应状态，不等于不需要成功连到测试端点，也不能把任何返回页面都当作目标服务可用。

  1. 备份配置，记下所看的入口、测试 URL、期望值和上次检查时间。确认界面显示的是定时健康检查，还是前端另外发起的手动测速。
  2. 对自己控制或允许访问的 HTTPS 测试地址，先确认正常情况下实际应该返回什么。若你能在同一节点上看到测试响应，只记状态与时间；出现登录页或跳转时，先核对端点是否仍适合健康检查，不用放宽匹配掩盖它。
  3. 一次只修订正确位置的一项配置：换成已确认的测试地址，或将预期值对齐该地址的设计；如果地址是订阅下发的，优先在可还原的本地配置副本测试，不改服务商原件。重载后等待实际检查运行；使用惰性检查时，先确认组或提供器节点在使用中。

结果分两行记

第一行记“检查位置｜测试主机｜预期／实际状态｜检查时间”；第二行记“同一节点｜实际用途｜是否完成”。健康检查恢复并且实际任务通过，才算两条都验收。若标红修复但工作页仍超时，转查那个工作页的路径，不把一次健康检查当作全网覆盖。
