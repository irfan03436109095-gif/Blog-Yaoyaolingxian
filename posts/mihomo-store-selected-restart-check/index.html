Mihomo 重启后选中的机场节点变了？核对 store-selected

加油2026-11-26— 次阅读
故障排查

用同一份机场配置时，昨天手动选了一个节点，今天打开客户端却看到另一个。先查当前是否在同一个手动策略组，再做一次只有核心重启这个变量的对照。这个方法适用于使用 Mihomo 内核且能查看运行配置或策略组的客户端。

确认客户端实际传给内核的配置

在客户端查看当前生效的配置或配置合并结果，找到策略组类型 select，确认你选的是这个组的一项直接成员。组里也可以包含自动组。若你手动留下的是自动组，重启后仍选中该组，但自动组内部选择可能变化。

Mihomo 文档中的 profile.store-selected 用于保存通过 API 选择的策略组成员，以供下一次启动使用。它属于根配置的 profile 项。如果你的客户端提供持久的本地覆写，可核对生效配置是否包含下面的字段。已有其他 profile 字段时，在原段落里核对或合并。

profile:
  store-selected: true

示意图。确认同一个手动策略组在重启前后是否保留了选择。

重启前后观察同一组

  1. 选择一个可辨认的候选项，记下当前配置名、策略组名和成员名。保持配置、订阅内容和设备网络不变。
  2. 用客户端提供的方式重启核心。若只关闭界面，核心可能仍在运行。重新打开面板后，先读同一策略组的选择。
  3. 用同一公开页面发起一条新连接。如果客户端有连接详情，核对该请求命中的规则及出站链，旧连接留作历史记录。

怎样解读两种差异

如果面板成员在重启时变化，先确认 store-selected 是否实际生效、前后是否加载了同一配置，以及原来的组名和成员名是否仍存在。若手动选择还在但实际连接走了另一组，核对这条请求的规则命中和自动组决策。做机场推荐对照时把组选择与新请求出口各留一条证据，就能看出差别发生在哪一层。
